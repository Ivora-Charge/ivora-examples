# Design: a fixed core plus switchable modules

**Status:** design for review. Nothing here is built yet: this document changes no code, no migration and no environment variable. Implementation starts only after review, in the tickets proposed at the end.

The CPO Starter Kit covers what an operator's own staff do every day. Optional features become **modules** that an owner turns on or off in the kit's settings. The kit is not a copy of the Ivora dashboard: anything about the operator's own account with Ivora, the platform provider (its platform billing, API keys, team access to the dashboard), stays in the dashboard and never comes into the kit. The operator's **own** Stripe account is a different matter: it is the operator's business, and the Host payouts module uses it directly (see [Host payouts](#host-payouts)).

All Ivora endpoint paths below are under `/v1/tenants/{tenant_id}` unless they start with `/payment/` or `/v1/billing/`, and were checked against the [published OpenAPI schema](https://api.ivoracharge.com/openapi.json) (contract version 2026-10-15). Scopes are the API key permissions the schema names. Stripe calls (Host payouts only) are named in words, not as Ivora paths, and go to Stripe's own API with the operator's key.

## Rules

These hold for the core and for every module.

1. **Public API only.** A module is offered only when every endpoint it needs is in the published API reference. No private, staff-only or administration endpoints (nothing under `/v1/admin/`), and no Ivora-hosted operation of the kit. Where the API is missing something, the module leaves that part out and the gap is listed in [Public API gaps](#public-api-gaps); it is never worked around.
2. **A switch hides UI; it is not a permission.** Turning a module off hides its screens and stops its jobs. It never grants or removes access. Permission is enforced twice, and never by the switch alone:
   - by the **Ivora API**, through the scopes of the deployment's API key (a call without the scope is refused by Ivora, whatever the switch says), and
   - by the **kit's server**, through the staff role (`requireRole()` and the database functions that re-check the role in the same statement as the write).

   Each module below names both.

3. **Modules that can change a charger or move money default to off** on a new deployment.
4. **Nothing about the operator's account with the platform provider.** This rule covers the operator's account with Ivora only: no Ivora platform billing, invoices or usage fees, no Ivora API key management, no Ivora dashboard team management, and no connection of the Stripe account that Ivora Checkout pays into (that is connected in the Ivora dashboard; the kit only reads its status). It does not cover the operator's own Stripe account used as a Stripe Connect platform for host payouts: that key belongs to the operator's deployment, is read from its environment, and is never committed, shown or sent to Ivora.
5. **Turning a module off changes nothing in Ivora.** It does not unpublish roaming sites, block cards or remove discounts from tariffs. The Modules page says so before an owner turns a module off (see [Disabled behaviour](#disabled-behaviour)).

Every default is off. Five modules can change a charger or move money (Host payouts; Remote commands; Firmware and diagnostics; Promotions; Fleet, because an accepted card starts charging with no payment), so rule 3 requires it. ### Site hosts (network mode)

- **Shows:** the Hosts page (`/hosts`), the Host role on the Team page, the Host filter on Chargers, Live and Reports, and host users' narrowed views (Overview, Chargers, Live, Reports; Pricing and Team per switch).
- **Switches per host depend on other modules:** "Restart and unlock" and "Start and stop sessions" are shown and allowed only with Remote commands on; "Receive fault emails" only with Station status emails on; "Edit prices" and "Invite further users" are core.
- **Payouts** are their own module, [Host payouts](#host-payouts), which needs this one on.
- **Narrowing sessions and bills with metadata.** Today a host's sessions and bills are read with one `station_id` query per charger. The published API also filters by metadata, so the module narrows with one query per host instead:
  - When a site is assigned to a host (and when a charger is added to or moved onto a host's site), the kit writes the tag `cpo_host` = the host's kit ID (an opaque UUID, no name) into the **station's** metadata with `PATCH /stations/{station_id}` (`stations:write`, with an `Idempotency-Key`). Unassigning a site, archiving a host or moving a charger off a host's site deletes the key (sent as `""`). The kit records per site when every one of its chargers carries the current tag.
  - **Sessions:** `GET /transactions?metadata[cpo_host]=<host>`. This filter matches the station's **current** metadata, so a host sees every session at its chargers, including those from before the tag was written: the same result as today's per-charger queries. `station_metadata` and `location_metadata` are snapshots taken when a session started, so they are not used for sessions: a site moved from one host to another would leave its history with the first host.
  - **Bills:** `GET /bills` has no current-station filter (its `metadata` filter matches the bill's own metadata, and `station_metadata` and `location_metadata` are snapshots). So the kit writes `cpo_host` into the bill's own metadata when it creates the bill at a host site (`POST /bills`, `metadata`), and reads `GET /bills?metadata[cpo_host]=<host>` for bills from then on. Bills older than the site's tag date, and bills at a site that changed host since, are still read per charger with `station_id`.
  - **Fallback:** while any charger of the host lacks a confirmed tag (a failed `PATCH`, a charger added in the Ivora dashboard), the kit uses the per-charger queries for that host. The settlement sweep re-applies missing tags.
  - **The tag narrows, it never authorizes.** Anyone with the key's `stations:write` can edit station metadata, so every row returned is still checked against the host's `cpo_host_sites` on the server, and a row outside the host's current sites is dropped (404 when asked for by ID), exactly as today.
- **Permission:** host access is decided on the server from `cpo_host_sites` on every request and re-checked by the database functions (`cpo_claim_host_command`, `cpo_set_host_station_pricing`, `cpo_create_host_invite`). Ivora sees one project and one key; the narrowing is the kit's. With the module off, a host user gets 404 on every page, because `requireNetworkReader()` refuses the host role.

### Host payouts

A money module. It needs Site hosts on: with `network` off it resolves to off whatever its own switch says, and the Modules page shows why.

- **The model.** The operator's own Stripe account acts as a **Stripe Connect platform**. Each site host that is paid out gets a **Standard** connected account of its own. A driver's payment at that host's site is a **direct charge** on the host's account; the operator's **network fee** is taken as the charge's **application fee**. Stripe pays the host's balance out to the host's bank on the host's own schedule, and Stripe's processing fee is the host's (as for any direct charge on a Standard account). No Ivora payouts API is needed or used, and Ivora Checkout is not used for these sessions. **USD only.**
- **Keys.** The platform secret key comes from the deployment environment (`STRIPE_SECRET_KEY`), and the Connect webhook signing secret from `STRIPE_CONNECT_WEBHOOK_SECRET`. Both are read on the server only (`lib/server/env.ts`), never committed, never shown on any page (the Modules page says only "set" or "not set"), never logged and never sent to Ivora. Without them the module can be switched on, but the page says payouts can't start and no host is paid out. The README's "the kit holds no Stripe keys" then holds only for deployments without this module; ticket 2 rewords it.
- **Shows:** a Payouts section on each host (on `/hosts/[id]`): connect status (not connected, onboarding, ready, restricted), a "Send onboarding link" button, the host's network fee, and the host's payouts summary. Host users see a read-only Payouts card on their Reports: their sessions' captured, refunded and network fee amounts from the kit's records. The kit does not read or show the host's Stripe balance or bank payouts; the host sees those in its own Stripe dashboard.
- **Onboarding.** An owner or manager starts it: the kit creates a Standard account for the host with the operator's key and an account link, and shows the link to send to the host. Readiness is the account's `charges_enabled`, read when the link returns and on each `account.updated` Connect event. The connected account ID (`acct_…`, not a secret) is stored in a new kit table with the host.
- **Network fee.** Per host, set by an **owner** only (it moves money): a percentage in basis points plus an optional fixed amount in cents. Computed in integer cents at capture: `fee = min(captured, round_half_up(captured × bps / 10000) + fixed)`, so it never exceeds the capture. A change applies to sessions that start after it; each session stores the terms it started with.
- **Checkout at a paid-out host's site** replaces the core's Ivora Checkout payment for that site, and keeps the core's hold, minimum and driver flow:
  1. `POST /charging-sessions` with the station, connector and tariff, `processor` `stripe`, `merchant_reference` the host's `acct_…` ID, `payment_reference` and `application_reference` from the kit's checkout ID, and `metadata` `cpo_host`. The kit refuses, and cancels the session (`POST /charging-sessions/{session_id}/cancel`), if the bill's currency is not USD.
  2. A PaymentIntent for the hold amount, created on the host's account (Stripe's `Stripe-Account` header) with manual capture and an idempotency key from the checkout ID. The driver pays on the kit's checkout page.
  3. When the authorization succeeds, the kit records it (`POST /charging-sessions/{session_id}/settlement-reports`, kind `authorization`), then `POST /charging-sessions/{session_id}/start` with funding confirmed and a `limit` of the hold amount, because Ivora does not stop an externally funded session at the hold on its own.
  4. The driver's stop button sends `POST /charging-sessions/{session_id}/stop`. When the session ends, the kit finalizes it (`POST /charging-sessions/{session_id}/finalize`), captures the final amount with the network fee as `application_fee_amount`, and reports the capture. Below the core's minimum, it cancels the PaymentIntent and reports a `release` instead.
  5. Every report uses the Stripe operation ID as `operation_reference`, so a retried report is deduplicated by Ivora. Ivora records these reports and never verifies them or moves money.
- **Refunds are the host's.** The charge is on the host's account, so the host refunds a driver from its own Stripe dashboard. Stripe does not return the application fee on such a refund. The kit receives the Connect event (`charge.refunded`), reports the refund to Ivora (kind `refund`), and shows on the host's Payouts section the fee share to return (the fee times the refunded share of the capture, in integer cents). An owner returns it **manually** with "Return network fee" (a Stripe application fee refund with the operator's key). It is never automatic and never more than the fee taken.
- **A paid-out host without a ready account.** Checkout at its sites is refused with "Payment isn't available at this charger right now" and the operator's staff see why. It never falls back to the core payment, which would collect the host's money into the operator's account (see the open questions).
- **Turning off.** New checkouts at host sites go back to the core's Ivora Checkout payment (the operator collects, as today). Sessions already started under the module are still stopped, finalized, captured and reported by the sweep, and host refunds of earlier charges are still recorded from the Connect webhook: in-flight money is always finished. Connected accounts stay connected in Stripe; the Modules page says so.
- **Permission:** the kit's role checks on the server (owner for the switch and fees and for returning a fee; owner, manager for onboarding; host users read only their own host). Ivora refuses the session calls without `billing:write`, `settlement:write` (create, start, reports) and `stations:control` (start, stop). Stripe refuses any call for an account that is not connected to the operator's platform. The switch only hides the UI and stops new checkouts.

### Fleet and RFID cards

- **Shows:** Cards (`/cards`, `/cards/[id]`), the private chargers list on Cards, and card ledger figures.
- **Background:** the card ledger refresh in the settlement sweep and on Cards page loads.
- **Permission:** `tokens:write` is granted only by a project admin in the Ivora dashboard. Turning the module off does not block any card: cards stay valid in Ivora. To stop cards working, block them first, or remove `tokens:write` from the key (the core's free charging and staff tokens are created once and then only read).

### Roaming

- **Shows:** Settings → Roaming.
- **Turning off:** the kit hides the page, but what Ivora publishes stays as last saved. The Modules page warns and links to Settings → Roaming to turn publishing off first.
- **Permission:** manager and owner on the server; `stations:write` for saving. Party approval and EVSE ID import stay with Ivora; the kit shows both and changes neither.

### Station status emails

- **Shows:** a recipients list on Settings → Modules (staff who opt in), the host switch "Receive fault emails", and the email itself.
- **Needs:** an email provider (`RESEND_API_KEY`, `EMAIL_FROM`) and the events above registered on the webhook (`npm run ivora:webhook -- register` adds them). Without a provider the module can be on but the page says no email is sent.
- **Background:** the webhook handler sends at most one email per charger and event kind per 15 minutes; a sweep step reads `GET /events` from a stored cursor to catch deliveries a webhook missed. Both skip when the module is off.
- **Permission:** reads only, `stations:read`. Recipients are chosen by managers and owners; host users get emails only for their own host's sites.

### Remote commands

- **Shows:** the command buttons in Live (start, stop, reset, unlock), availability (operative, inoperative) and the remote start and stop test in Chargers.
- **Without the module:** Live and Chargers stay, read only for charger state; the connection test (a read) stays. Driver checkout's own commands are core (see the footnote under [Core](#core-always-on)).
- **Permission:** the kit's role check (technician and up) and the host switches run on the server before any call. Ivora refuses a command without `stations:control`. Because driver checkout needs that scope too, the key always holds it: the kit's role check, not the switch, is what stops a viewer from sending a command.

### Firmware and diagnostics

A separate switch from Remote commands: a firmware update reboots a charger and is rarer than a reset, so an operator can allow resets without allowing firmware updates, and an upgraded deployment does not gain firmware updates automatically.

- **Shows:** a new Firmware panel on a charger's page: update from an `https` URL, upload diagnostics to an `https` URL, and the charger's reported firmware and diagnostics status.
- **Background:** the webhook handler's `station.firmware_status` and `station.diagnostics_status` steps, skipped when off.
- **Permission:** managers and owners on the server; not offered to host users. Ivora refuses the commands without `stations:control` (which the key always holds for checkout), so the kit's role check is what limits them. Ivora refuses `update_firmware` while a session is running (`409 transaction_active`); the kit shows that and never asks to force it.

### Promotions

- **Shows:** a Discounts section on a tariff in Pricing (card discounts, merchant validation codes and their discount), the adjustment in previews, and an optional "Validation code" field at driver checkout that is passed to `POST /bills`.
- **Card discounts use `id_tokens`, not `groups`.** A group discount applies to a bill's `pricing_group`, which only the creator of the bill can set (`POST /bills`, `pricing_group`). QR checkout drivers are anonymous: the kit knows no group for them and sends none, and a group typed in by the driver would be a discount anyone could claim. Cards carry no group in Ivora either (`TokenInput` has no such field; see the gaps). So the module offers discounts for listed cards (`id_tokens`) and merchant validation codes, and does not offer `groups`.
- **Rewards are not offered.** The public API has no loyalty balance, points or earned credit, so a rewards programme can't be built on it.
- **Turning off:** tariffs created with discounts keep them in Ivora. The Modules page lists the tariffs that still carry discounts; to end a promotion, save the tariff again without it (a new tariff version, as Pricing does today).
- **Permission:** managers and owners on the server (as Pricing); Ivora requires `tariffs:write` to create tariffs and `billing:write` for bills.

## The switch mechanism

### Storage

A new kit table, created by an additive migration in `supabase/migrations/` (named like the others, for example `2026112N0001_modules.sql`):

```sql
create table if not exists public.cpo_operator_modules (
  operator_id uuid not null references public.cpo_operators(id) on delete cascade,
  module text not null check (module in
    ('network', 'host_payouts', 'fleet', 'roaming', 'status_emails',
     'remote_commands', 'firmware', 'promotions')),
  enabled boolean not null,
  rev integer not null default 1,
  source text not null default 'owner' check (source in ('owner', 'upgrade')),
  updated_by uuid references auth.users(id) on delete set null,
  updated_at timestamptz not null default now(),
  primary key (operator_id, module)
);
```

- It follows the 10-30 rule: RLS on, all privileges revoked from `public`, `anon` and `authenticated`, no Data API grant. The server reads it with the service role.
- One function writes it: `cpo_set_module(p_actor uuid, p_operator uuid, p_module text, p_enabled boolean, p_expected_rev integer)`, `security definer`, with `search_path` set, `EXECUTE` revoked from `public`, `anon` and `authenticated` and granted to `service_role` only. In one statement it locks the actor's `cpo_staff` row, refuses unless the actor is still an **owner** of that operator, refuses if the row's `rev` is not `p_expected_rev` (0 for no row: someone changed it in between, so the page asks to reload), and upserts the row with `rev + 1`.
- The module list is a constant in `lib/modules.ts`, the same list as the `check`, with each module's dependency (`host_payouts` requires `network`). A module that is not offered (rewards) is not in the list at all.
- **Demo mode** keeps switches in the browser's demo cookie, like the demo team and demo cards, with a reset button. Nothing is written anywhere.

### Who may change it

- **Owners only**, on Settings → Modules (`/settings/modules`). Managers see the same page read only. Technicians and viewers do not see it (404). Host users never see it.
- The server action calls `requireRole("owner")`, then `cpo_set_module`, which checks again in the same statement. After a change the server logs the actor's user ID, the module and on or off (no email).
- The page shows, for each module, what it shows, the API scopes it needs and the role checks it keeps, so an owner knows which permissions to add to the key in the Ivora dashboard. The kit cannot read the key's scopes (see gaps); a missing scope shows Ivora's error code where it is needed, as today.

### Environment defaults

For one-click deploys, each module has an environment variable that sets its default:

| Variable                 | Module                   |
| ------------------------ | ------------------------ |
| `MODULE_NETWORK`         | Site hosts               |
| `MODULE_HOST_PAYOUTS`    | Host payouts             |
| `MODULE_FLEET`           | Fleet and RFID cards     |
| `MODULE_ROAMING`         | Roaming                  |
| `MODULE_STATUS_EMAILS`   | Station status emails    |
| `MODULE_REMOTE_COMMANDS` | Remote commands          |
| `MODULE_FIRMWARE`        | Firmware and diagnostics |
| `MODULE_PROMOTIONS`      | Promotions               |

- Values: `on` (also `1`, `true`, `yes`) or `off` (also `0`, `false`, `no`), any case. Unset, empty or `demo` means "no default": the built-in default (off) applies. Any other value is ignored with a warning on the Set up page and the Modules page, and the built-in default applies.
- `FLEET_MODULE`, the variable the kit reads today, stays as an alias of `MODULE_FLEET`. When both are set, `MODULE_FLEET` wins.
- They are read on the server only (in `lib/server/env.ts`) and listed in `.env.example` and the README's variable table.

**Resolution**, on the server, once per request:

1. A row in `cpo_operator_modules` for this operator and module: its `enabled` wins.
2. Otherwise the module's environment variable, if it is `on` or `off`.
3. Otherwise the built-in default: off.
4. Then dependencies: a module whose required module resolves to off is off too (`host_payouts` without `network`). Its own row or variable is kept, so turning `network` on again restores it.

So an environment variable sets the starting state, and an owner's choice in the kit then overrides it. To return a module to the environment default, the Modules page has **Use the deployment default**, which deletes the row (through the same function, with the same checks).

### Disabled behaviour

When a module resolves to off:

- **Navigation:** its entries are hidden. `modulesFor()` and `visibleModules()` take the resolved switches instead of `{ fleet }`. Parts of core screens that belong to the module are hidden too (Live's command buttons, Chargers' remote test step, the Pricing discounts section, the Settings → Roaming tab, the host switches that depend on it).
- **Routes return not found:** every page and layout of the module calls `requireModule(key)` first, which calls `notFound()`. It runs before the role check, so a disabled module answers 404 to everyone, the same as a route that does not exist. Route handlers that belong to a module answer `404` with no body.
- **Server actions refuse:** each action of the module calls `requireModule(key)` first and returns a not-found error without calling Ivora or writing to the database. A form left open in a browser when the module was turned off therefore does nothing.
- **Background jobs do not run:** the settlement sweep skips the module's step (the card ledger; the status events catch-up; the host tag repair). The webhook handlers verify the signature, record the event ID and acknowledge with `2xx` as today, but do not run the module's handler (fault and status emails; firmware status; Connect onboarding updates). Events skipped while off are not replayed when the module is turned on again, because handlers treat webhooks as signals and read the current state from the API.
- **One exception, for money:** sessions that Host payouts started are finished whatever the switch says. The sweep still stops, finalizes, captures or releases them and reports the outcome, and the Connect webhook still records refunds of their charges. Otherwise turning the module off would leave a driver's hold open or a host's refund unrecorded.
- **Data is kept:** turning a module off deletes nothing in the kit or in Ivora. Turning it on again shows the same hosts, cards and settings. The card ledger has a gap for the time the module was off, and its page says from when its figures are complete.
- **Turning off warns** with what stays active: roaming publication, cards that can still charge, tariffs that still carry discounts, host logins (kept but refused), hosts' connected Stripe accounts (still connected) and payouts sessions still running (finished as above).
- **Tests** per module: with the switch off, the page answers 404, each action refuses with no Ivora call (`fetch` stubbed to fail), the nav hides the entry, and the sweep or webhook step is skipped.

## Public API gaps

One line each. These are reported, not worked around.

1. Ivora Checkout payments take no destination account or application fee, so a host's share can't be split through Ivora Checkout; Host payouts uses externally funded sessions and the operator's own Stripe account instead (no provider payouts API is needed).
2. `GET /stats` has no `station_id`, `location_id` or metadata filter, so a host's report has no Ivora figures.
3. `GET /transactions` has no ID token filter.
4. Transactions show only the last 4 characters of the ID token, so card figures are matched by those.
5. A token can't be limited to some stations or locations (`TokenInput` has no such field).
6. `PATCH /tokens/{token_id}` takes no precondition (no `If-Match` or expected `updated_at`).
7. A token carries no pricing group (`TokenInput` has no such field), so group discounts can't follow a card.
8. No loyalty or rewards resource (points, balances, earned credit).
9. `GET /v1/access` has no documented response schema, so the kit can't tell an owner which scopes its key lacks before a module is turned on.
10. `GET /bills` has no filter on the station's current metadata, so bills from before a host tag are still read per charger.

## Migration for existing deployments

Today four of the eight module features are always on, one is behind `FLEET_MODULE` and three are not built:

| Feature today                                                     | Becomes              | On upgrade                                                               | New deployment |
| ----------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------ | -------------- |
| Hosts page, host users, Host filter (always on)                   | `network`            | **On**, seeded by the migration                                          | Off            |
| Cards (`FLEET_MODULE`)                                            | `fleet`              | **As today:** no row is seeded, so `FLEET_MODULE` (now an alias) decides | Off            |
| Settings → Roaming (always on)                                    | `roaming`            | **On**, seeded                                                           | Off            |
| Host fault emails (always on, per host switch)                    | `status_emails`      | **On**, seeded, so the host switch keeps working                         | Off            |
| Live start, stop, reset, unlock; Chargers remote test (always on) | `remote_commands`    | **On**, seeded                                                           | Off            |
| Host payouts (not built)                                          | `host_payouts`       | **Off**, not seeded: new, and it moves money                             | Off            |
| Firmware and diagnostics (not built)                              | `firmware`           | **Off**, not seeded: new, and it changes chargers                        | Off            |
| Staff status emails, promotions (not built)                       | Parts of the modules | Arrive off inside their module: built after upgrade, they are new UI     | Off            |

- The migration that creates `cpo_operator_modules` also inserts, for every existing row of `cpo_operators`, rows for `network`, `roaming`, `status_emails` and `remote_commands` with `enabled = true` and `source = 'upgrade'` (plain `insert … select … on conflict do nothing`, no `do` block). A fresh database has no operator when the migration runs, so it seeds nothing, and the first owner starts with every module off unless the deployment sets `MODULE_*` variables.
- So nothing disappears on upgrade: every screen that is on today stays on until an owner turns its module off. Seeded rows show "On since the upgrade" on the Modules page.
- `host_payouts` and `firmware` are never seeded: they did not exist before, so an upgrade gains neither money movement nor firmware updates until an owner turns them on. With `network` seeded on, Host payouts can be turned on without any other step but the Stripe keys.
- Turning Site hosts on (seeded or by an owner) starts writing the `cpo_host` tags; until each host's chargers are tagged, its reads use the per-charger queries, so host views look the same during the upgrade.
- The release notes for the version that ships the switches tell owners to review Settings → Modules and list what each switch hides.

## Open questions for review

- **Owners only:** should managers also be allowed to change switches that neither change a charger nor move money (Site hosts, Roaming, Station status emails)? This design says owners only, for one simple rule.
- **Remote commands off on new deployments** hides the chargers' remote start and stop test, a step many operators use when installing. Alternatively the test could stay core as a technician tool. This design follows the rule that anything that can change a charger is off by default.
- **A paid-out host without a ready Stripe account:** this design refuses checkout at its sites rather than collect the host's money into the operator's account. Should the operator be able to choose "collect for now and settle with the host later" per host instead?
- **Fee return amount:** this design returns the network fee in proportion to the refunded share. Should an owner be able to return a different amount (up to the fee), for example none on a partial goodwill refund?
