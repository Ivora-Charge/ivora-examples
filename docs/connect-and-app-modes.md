# Design: Connect your Ivora project, and install as an app

Status: **design for security review. No product code, and no template changes, come with this document.** No build ticket is made Ready until the review is done. Start with the Ampleaf template ([`cpo-starter-kit`](../cpo-starter-kit)), after its polish mockups are chosen.

**Decided by the owner:** Connect runs on the Ivora-run hosted demos within fixed limits, and this design is published. On the hosted demos Connect is **read-only and session-only**: read scopes only and no write consent at all, no refresh token stored, nothing from the visitor's project persisted, the connection ends with the browser session or after a short fixed time, Disconnect revokes the access token, and the "Live data from your project" banner is always shown. **Forks** may offer the full flow on their own deployment, including write scopes behind a second consent and rotating refresh tokens. The [neutrality rules](neutrality.md) carry the matching exception.

Every identifier below (client IDs, URLs, tokens, secrets) is a placeholder. Everything this design expects from Ivora is **planned, an assumption to confirm**, listed once in [Assumptions about Ivora OAuth](#assumptions-about-ivora-oauth-planned-to-confirm) and referenced as **(A1)**, **(A2)** and so on. Where an assumption turns out wrong, the design names what changes.

## Why

Today a template reads Ivora with one long-lived API key in its deployment settings, and the hosted demos show sample data only. An operator who wants to try a template on their own account must create a key, copy it and deploy. With an OAuth authorization (authorization code with PKCE, A1) a visitor could connect one project to a demo and see their own chargers, sessions and prices with no key and no deployment.

This design adds two modes next to the existing API-key mode. The five-minute API-key start does not change.

| Mode        | Who holds the credential                         | Typical use                                                                                                         |
| ----------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| **API key** | Deployment settings (today)                      | A fork running for one operator                                                                                     |
| **Connect** | A short-lived OAuth connection, per visitor      | Trying a demo on your own project, read-only by default (always read-only and session-only on the hosted demos, §6) |
| **App**     | Client credentials, one installation per project | A deployment that serves several operators, as an app                                                               |

## Assumptions about Ivora OAuth (planned, to confirm)

Ivora's third-party OAuth and app install are not generally available yet. Every item below is **planned / an assumption to confirm**; none is stated as fact. Each is checked against the Ivora OAuth reference before the build ticket that relies on it is made Ready.

## 1. The Connect flow on a demo

Demo mode stays the default. A visitor who does nothing sees sample data exactly as today. Steps marked **hosted** and **fork** differ by deployment; everything else is shared.

1. **Button.** The demo banner gains a second action: "Connect your Ivora project". It is a plain `POST` form to `/connect/start` (not a link, so crawlers and prefetch never start a flow).
2. **Start.** The server creates a random `state` and a PKCE `code_verifier`, stores both server side (the verifier itself, encrypted, because the token exchange needs it; a hash would be useless) in a pre-login record bound to a short-lived pre-login cookie `__Host-connect_pre` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 10 minutes, one use), and redirects the browser to Ivora's authorization endpoint (A1) with `response_type=code`, the client ID, the exact registered redirect URI, the requested scopes (read scopes only on the hosted demos), `state`, and `code_challenge` (S256). The pre-login record also stores which Ivora environment the flow was started against.
3. **Consent (on Ivora).** The visitor signs in to Ivora if needed, picks one project (A5) and sees the requested scopes (A6). The demo never sees the visitor's Ivora password. The consent screen is Ivora's; the demo only chooses which scopes to request.
4. **Callback.** `GET /connect/callback?code=…&state=…`. The server checks the pre-login cookie, compares `state` in constant time, consumes the record, checks the issuer (A13), and exchanges the code with the stored `code_verifier` for tokens (server to server). On `error=access_denied` it returns to demo mode with a neutral message. The callback never redirects to a URL taken from the request.
5. **After connecting.** The server creates a demo session (random 256-bit ID in a `__Host-demo_session` cookie, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`) mapped to the connection, then redirects to the overview. The browser never receives an Ivora token.
   - **Hosted:** the session cookie is a browser-session cookie (no `Max-Age`). The server keeps only the encrypted **access token**, its expiry, the granted scopes and the project ID from the token response (A5), in the session record. **No refresh token is stored** (A14). Nothing else from the project is written anywhere.
   - **Fork:** the server stores the connection with the encrypted access and refresh tokens and the project ID (§3, Forks).
6. **What the demo shows.** The same screens as today, fed by the visitor's project through the same server-only Ivora client: sites, chargers and connectors with status, sessions, prices (tariffs), reports and the Live page. Screens that depend on the template's own database (team, onboarding forms, checkout and settlement records, QR stickers) keep showing labelled sample data, because the demo has no records of the visitor's operation. The page says so ("Sample data: this screen is not connected").
7. **Banner.** While connected, every page shows a persistent banner: **"Live data from your project"**, with the project name (read per request, not stored), a read-only badge, when the connection ends, and a **Disconnect** button. It cannot be dismissed and is always shown while connected. The sample-data banner is replaced, never shown together with it on the same data. **Hosted:** the badge is always "Read-only"; there is no "Allow changes" action. **Fork:** after the second consent (§2) the badge names the approved write groups.
8. **Disconnect.** `POST /connect/disconnect` revokes the token at Ivora (A1), deletes the session and anything keyed to it, clears the cookie, and returns to demo mode. **Hosted:** it revokes the access token. **Fork:** it revokes the refresh token, which ends the grant. If revocation fails, the local deletion still happens and the page tells the visitor how to remove the connection on Ivora's side (A4).
9. **End of the connection.** The connection never outlives its demo session.
   - **Hosted:** the connection ends when the browser session ends or after the **fixed connection time** (§3), whichever comes first, and never later than the access token's own expiry. There is no refresh. At the end the server revokes the access token (when the end is noticed server side) and deletes the session record; the next request shows demo mode with "Your connection ended. Connect again."
   - **Fork:** when the session ends (idle limit or maximum age, §3) the connection is revoked and deleted with it. When Ivora rejects the refresh token (expired, removed, or reused), the next request deletes the connection and shows the same message.

Nothing is sent to Ivora on a visitor's behalf except reads (and, on a fork only, after the second consent, the writes of §2). A demo with no connected visitors has no stored tokens at all.

## 2. Scopes

The scope names are the permissions Ampleaf already documents in its [README](../cpo-starter-kit/README.md#permissions-per-module) (A7). A token carries only the scopes approved on the consent screen; the demo additionally hides what the token cannot do.

**Rule: read-only by default; read-only always on the hosted demos.** The first consent requests read scopes only. On the **hosted demos** that is the only consent: no write scope is ever requested, there is no "Allow changes" action and no second consent, and write actions are shown disabled with "Not available in the hosted demo. Run your own copy to make changes." On a **fork**, write actions stay disabled (visible but greyed, with "Needs write access") until the operator approves write scopes in a **second, separate consent**: a deliberate "Allow changes" action in the banner starts a new authorization request for the extra scopes, shown on its own consent screen (A9). It is never bundled into the first request, and never pre-triggered by clicking a disabled button.

### Minimum scopes per Ampleaf feature

| Feature                                   | Read-only (first consent; all the hosted demos request) | Fork only, after the second consent (write)                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overview (sites, chargers, live sessions) | `stations:read`, `billing:read`                         | none                                                                                                                                                    |
| Live (status, faults, sessions)           | `stations:read`, `billing:read`                         | Commands (start, stop, reset, unlock): `stations:control`; the first remote start also `tokens:read`, `tokens:write`                                    |
| Pricing (view tariffs, preview)           | `stations:read`, `billing:read`                         | `billing:write` (new tariff version, retire)                                                                                                            |
| Reports                                   | `stations:read`, `billing:read`                         | none                                                                                                                                                    |
| Chargers (list, status)                   | `stations:read`                                         | `stations:write` (add a site or charger, move a charger); the remote start/stop test: `stations:control`, `billing:read`, `tokens:read`, `tokens:write` |
| Cards (optional module)                   | `stations:read`, `billing:read`, `tokens:read`          | `tokens:write` (add, block, import)                                                                                                                     |

The read-only request is the union of the read column: `stations:read`, `billing:read`, and `tokens:read` only when the Cards module is on.

### Write groups (forks only)

The second consent, the write groups and `CONNECT_ALLOW_WRITES` exist only on forks running the full profile (§6); the hosted demos have none of them. Write approval is requested per group, so an operator who only wants remote control approves that group alone:

| Write group    | Scopes requested in the second consent            | Unlocks                                            |
| -------------- | ------------------------------------------------- | -------------------------------------------------- |
| Remote control | `stations:control`, `tokens:read`, `tokens:write` | Live commands, the Chargers remote start/stop test |
| Pricing        | `billing:write`                                   | New tariff version, retire                         |
| Chargers       | `stations:write`                                  | Add a site or charger, move a charger              |
| Cards          | `tokens:write`                                    | Add, block, import cards                           |

**The write UI is gated by the approved group, not by the scope alone.** Groups share scopes: approving Remote control grants `tokens:write`, which on its own would also allow Cards writes. The connection therefore records which groups the operator approved, and a feature's write actions are enabled only when its own group is approved and every scope of that group is in the granted set. Approving Remote control leaves Cards writes disabled until Cards is approved in its own consent.

Every remote command on a fork's connected demo (start, stop, reset, unlock, the charger test) asks for a confirmation that names the charger and the project and says it acts on real hardware; the first remote start also says it creates an authorization token in the project. The party running a fork can turn the second consent off entirely with `CONNECT_ALLOW_WRITES=false`.

### Unavailable in a connected demo altogether

These stay disabled or sample-only in every connected demo, hosted or fork, even with write scopes, because a demo must not do them for a visitor:

- **Onboarding.** Driver-page branding and logo, registering and verifying a return domain, and the Stripe status belong to the operator's own deployment and domain.
- **Driver checkout and payments.** No bills, holds, captures or refunds in the demo, and no QR stickers pointing at a demo domain. Checkout needs the operator's own Stripe account and their own domain.
- **Roaming (OCPI publishing).** A demo never publishes or changes a project's roaming data.
- **Webhook registration** (`webhooks:write`) and any settlement sweep: a demo never registers endpoints in a visitor's project, so Live polls instead of using webhooks.
- **Deleting sites or chargers, and setting a new charger connection password.** One-way changes on production hardware; not offered even with `stations:write`.
- **Team, invites and sign-in** of the template's own users (see §4), and anything stored only in the template's database.

On the hosted demos every write action in the table above is also unavailable.

## 3. Token handling in a public-code demo

The code is public, so the design must hold when the attacker has read it. The rules shared by both deployments come first; then the hosted demos, which keep no refresh token and persist nothing from the project; then forks, which may run the full flow.

### Shared rules

- **Encryption at rest.** Every stored token is encrypted with an application key (AES-256-GCM, a per-row random nonce, the row ID as additional authenticated data). The key comes from a server environment variable and is never in the database or the repository.
- **Never** in the browser (no cookie, local storage, URL or HTML), never in application logs, error messages, analytics, or the response of any route. The Ivora client is `server-only`, as in the [conventions](conventions.md#api-keys-and-tenant-id-stay-on-the-server); log redaction treats `Authorization`, `code`, `state`, `code_verifier`, `refresh_token` and `access_token` as secret. The browser holds only the opaque demo session ID.
- **Host request logs.** The hosting platform's own request logs record the callback URL, including `code` and `state`, outside the template's control. That code is single use, short-lived and useless without the PKCE verifier, which exists only server side; the callback exchanges it immediately. The party running the deployment keeps request-log retention short.
- **Production deployment only.** The OAuth client variables, the encryption key and the session or connection store exist only in the production deployment. Preview builds and branch deployments never receive them, so they show no Connect button; the mode selection (§6) also refuses Connect mode in a preview environment even if the variables leak in.
- A sealed-cookie design (the encrypted token in the browser) is rejected: it puts token material on the visitor's device and makes server-side revocation on Disconnect unreliable.

### Project binding on every call

The session or connection record stores the project ID from the token response (A5). Every Ivora call takes the tenant ID from that record, never from a request parameter, route or form field, and the client checks before sending that the call's tenant ID equals the stored project ID. A mismatch, or (on a fork) a token response naming a different project than the stored one after a refresh, ends the connection and writes a security event.

### Caching

Connected reads are never shared between visitors and never written to storage:

- The in-memory read cache (30 seconds at most) is keyed by **session or connection ID** plus the request, never by URL or project alone, and is dropped on Disconnect. It is memory only, never a database, file or shared cache.
- Connected reads bypass Next.js data caching: every fetch passes `cache: 'no-store'`, nothing connected goes through `'use cache'`, `unstable_cache` or any other shared cache, and connected pages render dynamically per request (they read the session cookie). Responses carry `Cache-Control: private, no-store`.
- A test runs two connections in parallel against a mocked Ivora with different data and proves neither sees the other's results, and that the Ivora client is called with `no-store` for connected reads.

### Hosted demos: read-only, session-only, nothing persisted

- **No refresh token.** The hosted demo asks for an access token only (A14). If a refresh token comes back anyway it is never stored, cached or logged (A14 says what happens instead).
- **Access token only, for a fixed time.** The encrypted access token lives in the session record with its expiry, the granted scopes and the project ID. The connection ends after the **fixed connection time** (proposed: 15 minutes from connecting, never longer than the access token's lifetime, A2; open question 3) or when the browser session ends, whichever comes first. There is no idle extension and no refresh: to keep going, the visitor connects again.
- **Nothing from the visitor's project is persisted.** The demo writes no chargers, sessions, prices, project name, email, name or Ivora profile data of the visitor to any store. Reads are fetched per request and held only in the 30-second in-memory cache above. The session record holds a credential and the project ID needed for binding, and is deleted when the connection ends.
- **Read scopes only.** The client checks that the granted scopes are a subset of the read column (§2) and refuses a connection that holds more, revoking it.
- **Disconnect** revokes the access token (A1) and deletes the session record.
- **Key rotation** needs no re-encrypt job: no hosted record outlives the fixed connection time, so switching the key ends at most the open sessions, whose visitors connect again.

### Forks: the full flow

A fork may offer write scopes, rotating refresh tokens and the second consent. Everything in this section applies to forks only.

- **Refresh token:** server side only, in the fork's database, encrypted as above, with a key version column for rotation. The access token is held in the same row, encrypted, or in server memory only, and refreshed on demand (A2).
- **Session limits:** a demo session ends after **2 hours idle** or **24 hours** after connecting, whichever is first, and ending it revokes and deletes the connection.

#### Rotation and reuse

- Refresh tokens rotate (A3). The server refreshes under a row lock on the connection, so two concurrent requests from one visitor cannot both refresh. The lock is bounded: the Ivora token call has a 5-second timeout and the lock a matching lock timeout; a second request waits at most that long for the result and otherwise answers "try again" without refreshing itself.
- **Ivora rotated but the database write failed.** The old refresh token is now spent and the new one exists only in memory. The server never retries with the old token (that would look like reuse). It revokes the new refresh token from memory, deletes the connection (best effort), and shows "Your connection ended. Connect again."
- If Ivora reports a **reused** refresh token, treat the connection as compromised: delete it, revoke what can be revoked, show demo mode with "Your connection was closed for safety. Connect again", and write a security event without token content.
- `invalid_grant` from a refresh deletes the connection (§1 step 9). The server never retries a refresh in a loop.

#### The second consent

- "Allow changes" starts a new authorization request for one write group, whose pre-login record also stores the current demo session ID, the connection's project ID and the group requested.
- The callback accepts it only for the **same demo session** (the session cookie must match the stored session ID) and only if the token response names the **same project**. A grant for a different project is rejected: the new tokens are revoked, the existing connection stays as it was, and the page says "That was a different project. Changes were not allowed."
- On success the stored tokens, granted scopes and approved groups are replaced **in one transaction** under the connection's row lock, then the previous refresh token is revoked (A9). A failure leaves the previous connection intact.

#### Key rotation

The encryption key has a version. To rotate: add the new key as current and keep the old one for decryption only; a re-encrypt job decrypts every row with its recorded version and writes it back under the new one, in batches; once no row has the old version, remove the old key. Because no connection lives longer than 24 hours, waiting a day after switching the current key also drains old rows; the re-encrypt job is for an urgent rotation.

### What is stored, and for how long

| Deployment | Data                                                                                                                                 | Retention                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Hosted     | Pre-login record: `state`, the PKCE verifier (encrypted), environment                                                                | 10 minutes, deleted on use                                                                                          |
| Hosted     | Session record: hashed session ID, encrypted access token, its expiry, granted scopes, project ID, created                           | Until Disconnect, the end of the browser session, or the fixed connection time, whichever is first                  |
| Hosted     | Security events (project mismatch, scope mismatch, failed callback): event type and time only, no token, project ID or visitor data  | 30 days                                                                                                             |
| Hosted     | Ivora response data (chargers, sessions, prices, project name); refresh tokens                                                       | **Not stored.** Read per request and cached only in memory, 30 seconds at most; no refresh token is ever stored     |
| Fork       | Pre-login record: `state`, the PKCE verifier (encrypted), environment, and for a second consent the session ID, project ID and group | 10 minutes, deleted on use                                                                                          |
| Fork       | Connection: encrypted tokens, key version, project ID, granted scopes, approved groups, created, last used                           | Until Disconnect or the end of its demo session, whichever is first                                                 |
| Fork       | Demo session: hashed session ID, connection ID, created, last used                                                                   | **2 hours idle** or **24 hours** after connecting, whichever is first; ending it revokes and deletes the connection |
| Fork       | Security events (reuse, project mismatch, failed callback), without tokens                                                           | 30 days                                                                                                             |
| Fork       | Ivora response data (chargers, sessions, prices)                                                                                     | **Not stored.** Read per request and cached only in memory, 30 seconds at most                                      |

Expiry is checked on every request (an expired session is revoked and deleted before anything is shown), and a scheduled job every 15 minutes (5 minutes on the hosted demos) revokes and deletes whatever expired without a further request (the demo's existing cron mechanism, with a bearer secret). No deployment stores the visitor's email, name or Ivora profile data.

### How a fork configures its own OAuth client

A fork never uses the hosted demo's client. It registers its own with Ivora (A8) and sets, as server variables (all listed in `.env.example` with empty values):

| Variable                   | Purpose                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `IVORA_OAUTH_CLIENT_ID`    | The fork's registered client ID                                                                        |
| `IVORA_OAUTH_REDIRECT_URI` | Exactly one redirect URI on the fork's own https domain, registered with Ivora                         |
| `IVORA_OAUTH_SCOPES`       | Optional narrowing of the requested scopes                                                             |
| `CONNECT_ENCRYPTION_KEY`   | 32 random bytes (base64) for token encryption; `CONNECT_ENCRYPTION_KEY_PREVIOUS` during a rotation     |
| `CONNECT_PROFILE`          | `hosted` (default: read-only, session-only, no refresh token) or `full` (refresh tokens, write groups) |
| `CONNECT_ALLOW_WRITES`     | `full` profile only; `false` hides the second consent entirely. Not read in the `hosted` profile       |

The redirect URI is an exact match on Ivora's side; the template never builds it from request headers. A fork without these variables simply has no Connect button.

### Threats

| Threat                                       | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stolen demo database**                     | **Hosted:** the store holds no refresh tokens and no project data; at most the open sessions' encrypted access tokens, each read-only and valid for the fixed connection time at most, plus pre-login records that are useless without the matching cookie. **Fork:** tokens are encrypted with a key that is not in the database; no connection lives more than 24 hours; refresh tokens rotate (A3); no Ivora response data is stored; scopes are read-only by default. Residual risk for both: database plus key together. The key lives in the host's secret store, separate from the database credentials. |
| **Preview or branch build reaching secrets** | The OAuth client, the encryption key and the session or connection store exist only in the production deployment; previews get none and refuse Connect mode (§6).                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Malicious fork imitating the demo**        | It can only phish with its own client. The real client's redirect URI is exact-match registered on one domain; the README and banner name the demo's one canonical domain; the consent screen is expected to show the client name and domain (A6); the operator can remove a connection on Ivora's side (A4). The code is public and anyone may fork it, so this is reduced, not removed.                                                                                                                                                                                                                       |
| **Open redirect**                            | The redirect URI is fixed and exact. A `return_to` after connecting is not accepted from the request; the server redirects to a fixed path, or to a path from a short allow-list stored with `state`.                                                                                                                                                                                                                                                                                                                                                                                                           |
| **CSRF on the callback**                     | `state` bound to the `__Host-` pre-login cookie, single use, 10 minutes; PKCE verifier bound the same way; the start, Disconnect and (forks) "Allow changes" routes accept `POST` only and check `Origin`. A callback without a matching pre-login cookie is rejected without exchanging the code. Login CSRF (an attacker connecting their project to a victim's session) is prevented by the same binding.                                                                                                                                                                                                    |
| **Project swap**                             | Every call checks its tenant ID against the stored project ID; on a fork the second consent must return the same session and project, or it is rejected and revoked.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Scope creep**                              | Scopes are fixed in code per feature, not read from the request, and the demo compares the granted scopes in the token response with what it asked for and refuses a connection that holds more. **Hosted:** only read scopes are ever requested or accepted. **Fork:** the first consent is read-only; writes need the separate consent per group, and write UI is gated by the approved group, not the scope alone (§2). A new feature that needs a new scope is a code change reviewed with the scope table.                                                                                                 |
| **Cross-visitor data via caches**            | Cache keyed by session or connection ID; `no-store` for connected reads; dynamic rendering; a test with two connections (§3, Caching).                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Mix-up between environments**              | Today there is one client and one environment. A future production client is a separate client with its own callback path; the pre-login record stores the environment, the callback checks the issuer (A13), and the code is exchanged only at the recorded environment's token endpoint.                                                                                                                                                                                                                                                                                                                      |
| **Token in logs, errors or referrers**       | Redaction list above; the application never logs the callback URL; host request logs are covered above; the callback responds with a redirect and `Referrer-Policy: no-referrer`, so `code` is not leaked onward.                                                                                                                                                                                                                                                                                                                                                                                               |
| **Visitor session theft**                    | Both: `__Host-` cookie, `HttpOnly`, `Secure`, `SameSite=Lax`, random 256-bit ID stored hashed; no data is shown from another visitor's connection (every query is keyed by the session's connection ID). **Hosted:** browser-session cookie, fixed connection time, read-only, so a stolen session reads one project for minutes and changes nothing. **Fork:** 2 hours idle and 24 hours at most, and writes only within the approved groups.                                                                                                                                                                  |
| **Abuse of a connected demo as a proxy**     | The demo exposes only its own fixed routes, never a generic pass-through to Ivora; rate limits per session and per address; no writes on the hosted demos, writes on forks limited by §2.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Denial by connection flooding**            | Rate limit on `/connect/start`; pre-login records expire in 10 minutes; a cap on new connections per day.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 4. Not in scope: Ivora sign-in for a template's own users

Connect and app mode are about a template **reading and acting on an Ivora project**. They are not a login for the people who use the template. In a real deployment the operator owns those logins: staff of the CPO template sign in through the operator's own system (Supabase Auth in Ampleaf today), and drivers (who need no account in Ampleaf's checkout) never see Ivora. Ivora sign-in for operator staff or drivers is a separate decision with its own design, and nothing here assumes it. In a connected demo, the demo's own sign-in stays the labelled demo owner; the Ivora connection grants no role in the template's team.

## 5. Install as an app

The same template can register as an **Ivora app** that an operator installs into a project from Ivora (A11), instead of every operator forking and deploying their own copy.

- **Registration.** The party operating the deployment registers the app with Ivora, declaring its name, the scopes it needs, its install URL and its webhook URL. The registered scopes come from the **same scope table** as §2: the table in code is the single source, and the Connect flow and the app manifest both derive from it. A feature's read scopes are the app's required scopes; its write groups are optional scopes the operator can approve at install, unchecked by default, and gated per group as in §2. Features unavailable in a connected demo (§2) are not limited this way in app mode, because the operator runs the template for real; they are listed with their scopes as optional.
- **Install.** The operator approves the scopes for one project in Ivora, and Ivora tells the app about the installation (A11). The app stores an installation record: installation ID, project ID, granted scopes, status. The approval at install replaces the Connect consent screens.
- **Linking a template user to an installation.** The template's own users (§4) are not Ivora users, so the link is made once, with a **signed one-time install claim**. After install, Ivora sends the operator to the app's install URL with the installation ID. The app verifies the installation server to server with its client credentials, never trusting the URL alone, and issues a claim: random, stored hashed, bound to that installation, single use, 15 minutes. (If Ivora can sign such a claim itself, the app verifies Ivora's signature instead, A11.) The operator signs in to or signs up for the template and redeems the claim, which makes them the owner of that installation in the template; further staff are invited inside the template as today. An installation with no redeemed claim shows no data to anyone, and a claim cannot be redeemed twice or for another installation.
- **Credentials.** The app authenticates with client credentials (A12): a client ID and secret held in the deployment's server settings, exchanged for a short-lived access token for a given installation. Tokens are requested on demand, held in memory, keyed by installation ID, and never stored. The client secret is a deployment secret: server-only, production deployment only, never logged, rotated by the operator who runs the deployment.
- **One deployment, several installs.** Every request resolves the installation from the signed-in user's link (above), never from a request parameter the user controls, then requests a token for that installation and calls Ivora with the installation's project ID, checked as in §3. All data access is keyed by installation ID, in code and in the database (with the same RLS discipline as the [10-30 rule](conventions.md#supabase-and-the-10-30-rule)); a test creates two installations and proves one cannot read the other. Webhook deliveries are verified per [conventions](conventions.md#webhooks) and routed to the installation named in the event.
- **Uninstall.** An uninstall notification deletes the installation record, its user links and anything keyed to it, within one hour.
- **Neutrality.** A template does not become an Ivora-hosted service by being installable. The installable deployment is run by whoever registers the app, under their brand, as for any partner app; see [neutrality](neutrality.md). The hosted-demo exception there covers read-only, session-only Connect only; Ivora-run hosted demos do not run in app mode.

## 6. Switching modes by configuration

Mode is decided at startup from server variables, in one function with a test, in this order:

1. `DEMO_MODE=true`: demo, nothing else is read.
2. `IVORA_API_KEY` and `IVORA_TENANT_ID` (and Supabase) set: **API-key mode**, exactly as today. The five-minute start is untouched: the OAuth variables are optional and absent from the quick-start steps.
3. `IVORA_OAUTH_CLIENT_ID`, `IVORA_OAUTH_REDIRECT_URI` and `CONNECT_ENCRYPTION_KEY` set, no API key, production deployment: **Connect mode**: demo by default, per-visitor connections, in one of two profiles chosen by `CONNECT_PROFILE`:
   - **`hosted` (the default, and what the Ivora-run hosted demos run):** the read-only variant. Read scopes only, no second consent, `CONNECT_ALLOW_WRITES` is not read, no refresh token is requested or stored, the connection ends with the browser session or the fixed connection time, nothing from the project is persisted, and the banner is always shown. The code paths that store refresh tokens or request write scopes are not reachable in this profile, and a test proves it.
   - **`full` (forks only):** the full flow of §3, Forks: refresh tokens with rotation, the session limits, write groups behind the second consent, and `CONNECT_ALLOW_WRITES`.
4. `IVORA_APP_CLIENT_ID` and `IVORA_APP_CLIENT_SECRET` set: **app mode**.
5. Nothing set: demo.

Setting variables from two of modes 2 to 4 at once is a startup error that names the conflict, since the credential source would be ambiguous. An unknown `CONNECT_PROFILE` value is also a startup error, never a silent fallback to `full`. In a preview or branch deployment, modes 3 and 4 fall back to demo with a log line naming the reason (§3). Every feature asks one interface for "can I do X" (approved groups and granted scopes, or the API key's permissions), so the screens behave the same in all modes. API-key mode keeps showing a missing permission as Ivora's error code; Connect and app modes show "Needs write access", "Not available in the hosted demo" or "Not approved at install".

## 7. Environments

- **Hosted demo:** its OAuth client points at Ivora's **test environment**, never production, in line with "one project per deployment, test resources for previews" (A10). A visitor connects a test-environment project. The banner says "Connected to the Ivora test environment" and the project name.
- **Operator with a production account:** the Connect page does not fail with an error. It says plainly: "This demo connects projects in the Ivora test environment only. You can try it with sample data, connect a test-environment project, or run your own copy with an API key (about five minutes)", with a link to the README quick start. This is decided from configuration (the environments the deployment has a client for), not from a failed authorization attempt, so no visitor sees a raw error. A fork that later connects production projects uses a second client with its own variables, callback path and button, never one client with an environment switch (§3, mix-up).
- **While Ivora's third-party OAuth is not generally available (A10):** the hosted demos keep sample data only and show no Connect button, so nothing fails; Connect is a documented capability that a fork turns on once it can register a client.
